# 重点问答的人工改写

以下正文由改写脚本按题号合并，原标题和 Obsidian 锚点保持不变。

## Q002

**参考回答**

`const` 说明是否允许通过这个声明修改数据，`static` 管存储期或链接范围，`extern` 声明别处定义的符号。它们不是一组“加上就安全”的修饰符。

| 写法 | 含义 |
| --- | --- |
| `const int *p` | 不能通过 p 修改整数，p 可以换目标 |
| `int *const p = &x` | p 不能换目标，可以通过 p 修改 x |
| `const int *const p = &x` | p 和经它访问的值都不能改 |
| 函数内 `static` | 对象跨调用保留，直到程序结束 |
| 文件作用域 `static` | 符号只在当前翻译单元中使用 |
| `extern int value;` | 声明外部定义，不在这里重复定义变量 |

**项目关联**

异步 UART 缓冲需要活到 DMA 完成，用静态池解决存储期；共享状态还需要同步。头文件暴露必要函数，模块内部状态保持私有，减少跨文件随意修改。

**追问：`const` 数据一定在 Flash 吗？**

不一定。放在哪里由对象、编译器和链接规则决定；它也不保证没有其他可写别名。修改真正的 const 对象是未定义行为。C 与 C++ 文件作用域 const 的默认链接规则也不同。

**追问：返回 static buffer 就线程安全吗？**

不是。它不会因函数返回失效，但两个任务仍可能互相覆盖。应让调用者提供缓冲、按任务隔离或明确加锁，不能只加 const 解决。

## Q004

**参考回答**

先分清“内存位于哪里”和“对象什么时候有效”。指针变量还在，不代表它指向的对象仍然存活。

| 区域 | 典型内容 | 注意点 |
| --- | --- | --- |
| 栈 | 调用现场、局部自动变量 | 退出作用域后不能继续异步访问局部对象 |
| 堆 | 动态申请的对象 | 必须处理失败、释放和碎片 |
| `.data` | 有非零初值的可写静态对象 | 运行在 RAM，初值通常也占 Flash |
| `.bss` | 零初始化静态对象 | 启动时清零，运行时占 RAM |
| `.text/.rodata` | 程序和只读数据 | 具体物理位置由链接脚本决定 |

**为什么局部 DMA 缓冲不行？**

函数创建 `uint8_t tx[64]`，交给 DMA 后立即返回。DMA 还没读完，数组生命周期已经结束，栈空间也可能被下一次调用覆盖。这不是“偶尔发错”的优化取舍，而是错误的所有权设计。

可以用静态池、调用者长期持有的对象或受管理的动态对象，但都要保证发送结束前不复用。静态对象只解决存活，不自动解决多人同时写。

**项目关联**

新版 UART 的 8 KiB payload 池是静态存储，任务栈及部分初始化对象仍可能从 FreeRTOS heap_4 分配。它们最终都占 SRAM，只是分配来源不同；不能说用了静态发送池，整个项目就没有动态分配。

**追问：总空闲内存够，为什么申请仍失败？**

可能缺少连续块，也可能受对齐、管理开销或可访问区域限制。看最大可分配块和实际分配器，不只看总空闲字节。

## Q007

**参考回答**

这些函数的关键不是背名字，而是知道对长度、重叠和字符串结束符有什么要求。

| 函数 | 规则 | 常见错误 |
| --- | --- | --- |
| `memcpy` | 源与目标不能重叠 | 同一缓冲里移位却用它 |
| `memmove` | 支持重叠 | 忘了仍需检查目标容量 |
| `strlen` | 输入必须已经有 NUL 结尾 | 用它计算任意二进制包长度 |
| `snprintf` | 限定写入容量，返回需要的字符数 | 把截断后的返回值当实际发送长度 |
| `strncpy` | 不保证总有 NUL 结尾 | 认为“名字带 n 就绝对安全” |

**`snprintf` 应怎么检查？**

```c
char buf[64];
int n = snprintf(buf, sizeof(buf), "value=%u", (unsigned)value);
if (n < 0 || (size_t)n >= sizeof(buf)) {
    /* 格式错误或截断：不按 n 字节发送。 */
    return;
}
/* n 是本次字符串的字符数，不含末尾 NUL。
   若异步发送，还必须保证 buf 的生命周期。 */
```

假如需要 100 个字符，容量只有 64，函数可能返回 100。让 DMA 发 100 字节会越界读取。二进制包中出现 0 字节也不代表包结束，按协议长度处理。

**项目关联**

扩展状态回复时，大局部数组和格式化调用曾增加任务栈压力。高频 ISR 不做长字符串格式化；普通任务也要同时检查容量、格式类型、返回值和栈预算。

**追问：格式化成功就可以把局部 buf 交给 DMA 吗？**

不一定。函数返回后 buf 会失效，必须同步完成或复制进受管理存储，或者直接在最终 DMA 租约中格式化。参见 Q033/Q034。

## Q010

**参考回答**

编译链把源代码逐步变成可运行镜像；每一步解决的问题不同。

```text
源代码 → 预处理：展开宏/include
       → 编译：生成汇编或编译器中间表示
       → 汇编：生成可重定位目标文件
       → 链接：解析符号、重定位、按链接脚本布局
       → ELF → 转换为 BIN/HEX（用于对应烧写流程）
```

| 文件 | 保存什么 | 用在哪里 |
| --- | --- | --- |
| ELF | 段、地址、符号与调试信息 | GDB、map 对照、反汇编、日志字典提取 |
| BIN | 原始镜像字节 | 必须由烧写方指定正确地址 |
| Intel HEX | 带地址和校验的记录 | 按工具支持的地址记录加载 |

**项目关联**

A/B 不只是两个文件名。要分别核对链接起址、`.isr_vector`、APP 槽位身份、升级目标和镜像 CRC。把 A 镜像改名为 B，不会自动改变它的地址或身份。

tokenized 日志字典保留在 ELF 的相关信息段中，通常不进入烧录 BIN；只留 BIN 可能无法正确离线解码日志。

**追问：`undefined reference` 和 `multiple definition` 分别是什么？**

前者是链接时找不到正确实现，检查源码是否参与构建、C/C++ 名称、库及链接命令；后者是重复定义或重复加入构建。声明能通过编译，不代表实现已经正确链接。

## Q012

**参考回答**

Modern CMake 按 target 管理依赖与使用要求。PUBLIC、PRIVATE、INTERFACE 决定一项要求由谁使用、是否传播给使用者。

| 关键字 | 当前 target 使用 | 使用者继承 |
| --- | --- | --- |
| PRIVATE | 是 | 通常不传播这项使用要求 |
| PUBLIC | 是 | 是 |
| INTERFACE | 否 | 是 |

例如库公开头文件出现另一个库的类型，消费者也需要相应头文件路径，通常要传播要求；只在实现内部用到的配置，不必污染所有消费者。

```cmake
target_include_directories(protocol PUBLIC include)
target_link_libraries(protocol PRIVATE internal_codec)
```

这段是说明依赖可见性的例子，不是项目原文件。静态库最终链接仍可能需要它的内部依赖，所以 PRIVATE 不等于“下游最终永远不链接这个库”。

**项目关联**

toolchain 指定交叉编译器与查找规则；Presets 区分 Debug/Release 和诊断选项。我的 A/B、SafetyLocked 及隔离版本使用独立构建目录，防止 CMake cache 串用。新试验选项默认关闭并检查互斥组合。

**追问：为什么不把 include 和 flags 全设成全局？**

会让无关模块继承配置，依赖关系不清晰，迁移和排错更难。按 target 配置更容易看出哪个模块需要什么，也减少本机绝对路径泄漏到库接口。

## Q018

**参考回答**

FreeRTOS 任务优先级和 NVIC 中断优先级是两套规则：任务通常数字越大越优先，中断通常数字越小越紧急。两者不能直接比大小。

| 对象 | 常见数值规则 | 怎样影响执行 |
| --- | --- | --- |
| FreeRTOS 任务 | 大数更优先 | 高优先级就绪任务抢占低优先级任务 |
| NVIC 中断 | 小数更紧急 | 更紧急 IRQ 可以打断允许被抢占的执行流 |
| PendSV | 设为低紧急度 | 在合适位置完成上下文切换 |

**为什么高紧急度 ISR 不能随便调用 RTOS？**

FreeRTOS 的临界区只屏蔽配置范围内的中断。范围外的高紧急度 IRQ 仍能进入；若它修改内核结构，就可能打断内核正在进行的更新。所以只有允许的中断优先级才能使用对应 `FromISR` API，且不能阻塞。

**项目关联**

项目常规配置的 RTOS API 边界是逻辑优先级 5，部分通信 DMA IRQ 设为 6；新版 SPI DMA IRQ 为 3，不调用 RTOS API，ADC 快速控制 IRQ 更紧急。实际还要核对 `configPRIO_BITS`、优先级分组及宏是否已经移位，不能把裸数字直接写进所有寄存器。

**追问：中断是 3，任务是 5，谁更优先？**

不能这样比较。IRQ 与线程调度不在同一编号空间；IRQ 按异常优先级打断线程，任务之间再由调度器选下一位。

## Q020

**参考回答**

先判断要“保护资源、通知事件，还是传递数据”，再选同步工具。

| 工具 | 典型用途 | 主要限制 |
| --- | --- | --- |
| mutex | 保护任务共享资源 | 可能阻塞；不能在 ISR 中等待；通常支持优先级继承 |
| 二值信号量 | 通知一次事件 | 连续事件可能合并，不能表示任意次数 |
| 计数信号量 | 计数事件或资源份数 | 容量有限，不自动传递完整数据 |
| 队列 | 传值或句柄 | 入队复制的是配置的 item；句柄指向的数据仍需管理 |
| 任务通知 | 通知一个指定任务 | 接收者固定，要明确 bit/计数/覆盖语义 |

**项目关联**

UART 只有一个 TX 任务启动 DMA，完成 ISR 通知它继续处理。多个生产者的分配/发布用原子核心，不再靠一把生产者 mutex；日志待发队列传共享句柄，payload 生命周期由引用管理。

旧版串口用锁保护写 ring，这是历史实现；新旧方案不能混讲。DMA 完成事件与“谁能改缓冲”也不是一件事。

**追问：二值信号量丢了两次通知怎么办？**

如果只需要“有活要做”，合并可能是设计允许的；若必须处理每一次事件，就要计数或队列。即使用通知唤醒，任务也要根据真实队列/硬件状态判断工作量，不只凭一次唤醒消费一条。

## Q089

**参考回答**

Modbus TCP 在功能码和数据前使用 MBAP 头，包含事务标识、协议标识、长度和 Unit ID；标准 Modbus TCP 不使用 RTU 帧末的 CRC。它不是把完整 RTU 帧不加区分地塞进 TCP。

| 项目 | Modbus RTU | Modbus TCP |
| --- | --- | --- |
| 承载 | 常见 UART + RS485 | TCP 字节流 |
| 边界识别 | 协议规定的帧时序、长度 | MBAP 长度字段 |
| 校验 | RTU CRC16 | 由 TCP 等底层校验传输；应用仍需校验语义 |
| 请求关联 | 地址/功能及事务时序 | Transaction ID 等字段 |

**TCP 为什么还有半包？**

TCP 保证有序字节流，不保存应用的一次 write 边界。一次 recv 可能只收到半个头，也可能拿到两个请求及下一个请求的开头。

解析器应先累积够 MBAP 头，校验协议标识和长度上限，再等完整 ADU，处理完继续解析剩余字节。超大长度、连接中断和超时必须有界处理，不能无限分配或永远等待。

**项目关联**

我的 TCP 网关只读 FC04，仍需要正确处理半包、粘包、事务匹配及异常响应。只读减少动作风险，不代表解析器可以省略长度检查。

**追问：用了 TCP，为什么还要业务确认？**

TCP ACK 只说明传输层接收了字节。设备是否执行、数据是否新鲜、数据库是否提交，都要由应用响应说明。

## Q103

**参考回答**

鉴权确认“谁允许访问”，TLS 保护通信并验证服务端身份，SSH 隧道把某个端口的流量安全转发到另一端。它们各自解决不同问题。

**`127.0.0.1` 为什么能看到云端？**

因为 SSH 在本机监听一个端口，再把这个端口的流量送到云端。浏览器访问的是本机入口，实际服务可以在远端；`127.0.0.1` 本身仍然永远表示发起连接的那台机器。

```text
电脑浏览器 → 电脑 127.0.0.1:转发端口 → SSH → 云端回环后端
ESP 上传 → 鲁班猫局域网入口 → SSH 隧道 → 云端回环后端
```

**项目关联**

ESP 不能填电脑或云端的 `127.0.0.1`，要填它实际能到达的鲁班猫 LAN 地址。热点密码、SSH 登录凭证和服务 API token 是三种凭证，不能互换，也不应发进聊天或提交仓库。

当前信任 LAN 上的 HTTP 加 SSH，不是 ESP 到云端的端到端 HTTPS。公网入口还需要证书、反向代理、鉴权、限流和防火墙策略；配置证书工具不等于入口已可用。

**追问：有 HTTPS 就可以公开运动控制吗？**

不可以。TLS 不替代业务权限、现场联锁、命令会话与安全验收。观测接口和动作权限应分别设计。

## Q001

**参考回答**

数组是实际存放元素的对象，指针是保存地址的变量。两者都能配合下标访问，但类型、大小和生命周期不同。数组指针指向一整组元素；指针数组则是“里面放指针的数组”。

| 声明 | 含义 | 加 1 的含义 |
| --- | --- | --- |
| `int a[4]` | 4 个连续的整数 | 数组对象本身不能自增 |
| `int *p = a` | 指向首个整数 | 跳过 1 个 `int` |
| `int (*row)[4]` | 指向含 4 个整数的一行 | 跳过整行，即 4 个 `int` |
| `int *ptrs[4]` | 存放 4 个指针的数组 | 其中每个指针分别指向自己的目标 |

例如二维数组 `int matrix[3][4]` 可以用 `int (*row)[4] = matrix` 遍历。`row + 1` 到下一行，`row[1][2]` 访问下一行的第三个元素。

**关键原理**

数组在多数表达式中转换为首元素指针，但 `sizeof(a)` 和 `&a` 等场景不这样转换。函数参数写成 `int a[]`，实际会调整为指针参数，所以函数内不能靠 `sizeof(a)` 求原数组长度。

`matrix` 转换后的类型是 `int (*)[4]`，不是 `int **`。二维数组靠固定行宽计算地址，二级指针则先读一个指针再访问目标，不能直接互换。

**项目关联**

DMA、CAN 解析和日志分片接口都要明确“地址 + 长度 + 所有权”。只传指针，接收方既不知道容量，也不知道什么时候可以释放这块内存。

**追问：`a` 和 `&a` 为什么看起来地址一样？**

它们从同一处内存开始，但类型不同。对 `int a[4]`，表达式中的 `a + 1` 跳过一个整数，`&a + 1` 跳过整个数组；地址数值相同不代表操作含义相同。

**保留我的补充理解**

数组指针就是保存每一行的起始地址，如果是二维数组的话就每次指针加一就跳一行

## Q003

**参考回答**

不能。`volatile` 约束的是编译器怎样访问一个对象，不提供互斥，也不把多个步骤合成一次原子操作。它常用于硬件寄存器；任务之间共享数据，仍要选择原子操作、锁或短临界区。

**为什么 `volatile counter++` 仍会丢更新？**

`++` 通常包含“读取 → 加一 → 写回”。计数是 5 时，两个任务都读到 5，最后都写回 6，而不是 7。即使单次对齐 32 位读写在目标平台上不可分割，也不能推出整个读改写原子。

| 机制 | 主要解决什么 | 不负责什么 |
| --- | --- | --- |
| `volatile` | 保留约定的可观察读写 | 互斥、线程同步、刷新硬件 Cache |
| 原子操作 | 单次原子访问及规定的内存顺序 | 自动保护任意一组字段 |
| mutex | 多个任务互斥访问资源 | 在高优先级 ISR 中阻塞等待 |
| 短临界区 | 在明确的执行范围内保护短操作 | 允许长时间等待串口或 Flash |

**项目关联**

新版 UART 用 32 位原子 CAS 预留缓冲，用 release 发布已经写好的描述符，消费者通过 acquire 获取。原子操作保护的是分配与发布规则；消息完整还依赖独占缓冲、先写后发布、DMA 完成后才回收。

这不代表整个项目都无锁。FreeRTOS 唤醒、日志历史管理和多字段快照各有自己的同步方式。

**追问：`DMB` 能代替原子操作吗？**

不能。`DMB` 是处理器的内存访问顺序约束，不会把 `counter++` 变成不可分割操作，也不能自动消除 C/C++ 数据竞争。DMA 的 Cache 一致性还要另行处理。

## Q013

**参考回答**

这些工具分别解决编辑、构建、环境一致性、代码格式和自动验证，不是用了其中一个就具备完整工程化。

| 工具 | 解决的问题 | 项目里怎么讲 |
| --- | --- | --- |
| VSCode | 编辑、跳转、调试入口 | 统一开发入口，不替代编译器 |
| GNU ARM Toolchain | 把代码编译成 MCU 程序 | 核对版本、ABI 和链接配置 |
| Modern CMake | 按 target 管理依赖与构建 | A/B 槽分别构建，避免全局配置互相污染 |
| Docker | 固定工具链和依赖环境 | 已有配置；当前环境未完成镜像实际构建运行 |
| clang-format | 自动统一代码排版 | 已配置并对明确范围的文件做格式检查 |
| CI | 自动构建、检查和测试 | 需要流水线实际运行记录，不能把配置文件当完成证据 |

**为什么 Docker 有价值？**

同一份代码在两台电脑上，可能因为编译器、库或生成工具版本不同而得到不同结果。容器可以固定这些依赖，减少“只在我电脑上能编译”的问题；还应固定基础镜像和版本，保存产物及构建日志。

**项目关联**

我的工程有 CMake 交叉构建、A/B 配置和主机测试。最新验收记录中，10 个明确范围的源文件通过 clang-format 检查，但 Docker 镜像没有实际运行。面试时分别说明配置完成、检查通过和实际构建通过，不把三件事合并。

**追问：格式化会不会改变程序功能？**

它的目标是排版，但仍要审查 diff 并重新编译、测试。首次引入时应限定范围，避免把大量无关格式变更混进功能修复。

## Q024

**参考回答**

任务栈存放函数调用现场、局部变量和保存的寄存器。大小不能靠“跑起来了”判断，要结合最深调用、最大局部对象、异常分支和实际高水位测量。

**确定栈大小的顺序**

1. 看创建接口的单位。在当前 Cortex-M FreeRTOS 端口中，512 个 32 位字等于 2048 字节；别把字和字节混用。
2. 看最深调用链、格式化函数和局部数组。RPC、Transfer、诊断打印会增加栈消耗。
3. 开启合适的栈溢出检查，读取 `uxTaskGetStackHighWaterMark`，覆盖长报文和错误路径。
4. 留余量，并区分任务栈、异常使用的 MSP 和可能的浮点上下文开销。

**项目关联**

项目出现过 ProtocolTask 状态回复栈不足，后来 Router 任务的 512 字栈也在诊断请求后被踩坏并触发 HardFault。修复不是只把数字增大，还要收紧局部缓冲、检查调用链，再实机读取余量。

10 月 6 日隔离并发测试记录的历史最小剩余量是：Router 2056 字节、Protocol 924 字节、Transfer 3612 字节。这只说明已执行路径有余量，不是全部分支已经证明不会溢出。证据见 [[20_真实网络Transfer与FOC并发_面试回答]]。

**追问：高水位还很多，为什么仍可能崩溃？**

可能测试没走到最深分支，也可能是越界写、悬空指针或 MSP 不足，而不是任务栈容量问题。要结合故障寄存器、调用栈和内存破坏位置排查。

## Q033

**参考回答**

我的主日志 UART 采用“固定发送池 + 多生产者发布队列 + 一个 TX 任务 + DMA”。生产者先拿到最终发送内存，在里面写好数据再提交；TX 任务把同一块内存交给 DMA，完成后才回收。

```text
多个生产者：Acquire → 原位写数据 → Commit
                                      ↓
一个消费者：取就绪批次 → 启动 DMA → 确认结束 → 归还内存
```

**实现要点**

1. payload 池是 8192 字节，分成 32 个 256 字节单元。申请 300 字节需要两个连续单元；另外还有描述符开销。
2. 用 32 位原子位图 CAS 预留单元。总空闲够但连续单元不足，申请仍会失败；池不会搬动正在使用的数据整理碎片。
3. `Commit` 成功后所有权交给发送端，生产者不能继续改数据或取消。未提交的租约才可 `Cancel`。
4. 发布链表按头插入，消费者 `atomic_exchange` 取走一批，再反转，恢复该批成功发布的先后顺序。顺序不是按申请时间决定的。
5. 完成 ISR 只通知任务。TX 任务确认 DMA 结束后回收，不在 ISR 中做大段格式化或复杂队列处理。

**项目边界**

无锁指分配和发布核心，不代表 RTOS 唤醒、可选等待及所有业务都无锁。新版 UART 已随 A/B 固件上板，115200 IAP、命令回复和回退有实机记录；2M 仍缺持续实机压力验收。详见 [[11_UART零拷贝改造_白话实现与验收]]、[[13_AB升级实机验收_20261005]]。

原生单包可申请至 8192 字节；保留的兼容 Write 入口拒绝长度大于等于 8192 的包，两种接口的边界不同。

**追问：超时了为什么不立刻释放？**

超时不代表 DMA 已经停止。只有终止成功并确认通道 EN 清零，才能归还内存；否则保持占用、停止接收新发送，避免别人覆盖 DMA 还在读取的数据。DMA 完成也不等于对端业务已处理。

## Q034

**参考回答**

零拷贝必须说清范围。在我的原生 UART TX 路径中，业务直接在最终 DMA 缓冲里生成帧，提交后 DMA 读同一地址，因此没有“生成整包后再复制进发送缓存”这一步。

编码、格式化仍需要 CPU，DMA 也仍要搬运内存中的数据。零拷贝不是完全不搬数据。

| 路径 | 当前做法 | 可以怎么表述 |
| --- | --- | --- |
| 原生 Acquire / Commit | 在最终池内生成，DMA 读同一地址 | 最终帧生成到 DMA 的传输层零拷贝 |
| 普通格式化打印 | 直接在发送池内格式化 | 不再用完整临时字符串复制入队 |
| 任意调用者的 Write / WriteReliable | 将调用者数据复制进受管理的池 | 兼容入口仍有一次复制 |
| Pigweed 待发、history、dump | 共享不可变日志记录，通过引用持有 | 这些缓存之间避免整条 payload 重复复制 |
| RX、Router、CAN、Transfer、云端 | 各自仍可能组包、序列化和复制 | 不能概括成整个项目端到端零拷贝 |

**为什么引用共享能工作？**

日志先在共享池生成并封存，队列和历史缓存只保存引用。发送端再持有一个引用，DMA 完成才释放；最后一个持有者释放后，记录才能复用。封存后不能修改，历史覆盖也不能释放仍在发送的记录。

**项目关联**

主机测试检查“生产者缓冲地址 = DMA 传入地址”，并分别统计原生帧、复制帧和复制字节。共享日志的后续改造见 [共享日志实现记录](<D:/new project/firmware_common/PIGWEED_SHARED_LOG_ZERO_COPY.md>)。这类证据证明指定软件路径，不等于实机整条链路从未复制。

**追问：把局部数组指针放进队列，不就零拷贝了吗？**

不行。函数返回后局部数组生命周期结束，DMA 可能读到失效或被覆盖的内存。必须有稳定地址、清晰所有权和完成后回收规则；先保证正确，再谈少一次复制。

## Q037

**参考回答**

SPSC 是一个生产者、一个消费者；MPSC 是多个生产者、一个消费者。区别在于：SPSC 可以让双方各自更新自己的索引，MPSC 则必须处理多个生产者同时抢位置、同时发布的竞争。

**我的 MPSC 怎样发布？**

生产者先独占缓冲，写完 payload，再把描述符通过 CAS 插入就绪链表。release 发布确保消费者拿到描述符后，能按同步约定看见已经写好的数据；消费者用 acquire 取得数据。

```text
依次成功发布 A、B、C
头插后的链表：C → B → A
消费者摘取并反转：A → B → C
```

`atomic_exchange` 一次摘走当前批次，之后生产者可以继续往新的头发布。反转是恢复这一批的发布顺序，不是为了反转消息内容，也不能按它推断“谁先申请谁先发送”。

**为什么慢生产者不会堵住别人？**

A 申请后被抢占，还没提交；B 写完并提交，就已经进入就绪链表，可以先被发送。申请与发布分开，消费者不必等某个尚未完成的预留位置。

**追问：原子操作是否保证每个发送者的整包完整？**

只保证规定操作不可分割，以及相应内存顺序。整包完整还依赖：缓冲独占、先写完再发布、提交后不修改、DMA 完成后才归还。一个租约不能复制给两个任务共同提交。分配和发布核心无锁，也不等于每个生产者都 wait-free；CAS 竞争时仍可能重试。

## Q040

**参考回答**

Router 是设备之间的消息转发层：根据目标节点选择端口，把消息送到对应设备。UART、USB 转串口、TCP Socket、CAN 适配是运输方式；Router 在这些方式之上统一寻址、转发和发现。

**我的项目链路**

```text
PC → TCP → 鲁班猫 Router → Wi-Fi → ESP32 Router → UART → STM32
```

Router 负责“送到谁”，`pw_rpc` 负责“调用哪个方法”，`pw_transfer` 负责“资源如何可靠分块传完”。它们分工不同，可以组合，不是三选一。

**实现要点**

包有源/目标节点、类型、序号、TTL、长度与校验；节点根据路由表选择出口。转发还要避免回送入站端口、限制 TTL、识别近期重复包，并使用有界队列。

HELLO 用于发现邻居、学习路由；节点和路由超时后失效。动态路由是根据实际发现更新表，不是事先写死所有路径，也不是互联网规模的成熟路由协议。

**项目关联**

已有 USB/UART、鲁班猫 Wi-Fi 多跳只读 RPC，以及真实资源 3 日志、资源 4 编码器快照的 Transfer 下载记录。测试工装角色仍包含软件模拟；端口枚举存在不代表所有实体设备都接入并验收。详见 [[14_Router多设备组网_白话实现与验收]]、[[20_真实网络Transfer与FOC并发_面试回答]]。

**追问：用了 SocketCAN 还需要 Router 吗？**

SocketCAN 提供 Linux 访问 CAN 的接口，Router 解决跨设备、跨端口寻址和转发。只做点对点 CAN 收发未必需要 Router；做多种链路组成的小网络时，两者可以配合。

**参考回答**

Bootloader 负责选择、校验和启动 APP；APP 负责正常业务、接收升级数据及试运行健康确认。采用 A/B 的主要目的，是更新非活动槽时保留当前可用镜像，避免一次失败直接破坏唯一程序。

| 部分 | 主要职责 | 不该混淆的事 |
| --- | --- | --- |

**追问：A/B 就一定不会变砖吗？**

不是绝对保证。Bootloader、元数据更新、双副本位置和恢复路径都可能出错。只能结合故障模型和断电、坏镜像、启动失败测试，说明在已验证范围内怎样恢复。

## Q047

**参考回答**

升级不是“收完文件就跳转”，而是从准备、写入、校验、试运行到确认的一组状态。每一步都要规定成功条件、失败处理和复位后怎样继续。

```text
IDLE
  → PREPARE：确认安全状态和非活动槽
  → RECEIVING：按位置写入，检查长度/顺序
  → VERIFY：检查整镜像长度、CRC、向量与槽位信息
  → PENDING：持久化试运行请求
  → TRIAL：Bootloader 启动新 APP，限制尝试次数
  → CONFIRMED：新 APP 通过健康检查后确认

接收/校验失败：旧确认槽仍可启动
试运行失败或未确认：复位后按元数据规则回退
```

**几个关键设计**

1. 未完整验证的镜像不能成为正常启动候选。包 CRC 只能验证包，整镜像仍需独立检查。
2. 新槽先写好、校验好，再发布元数据，避免把半写入镜像标成有效。
3. trial 与 confirmed 分开。能启动不代表关键任务已经创建、通信正常、输出状态安全。
4. Python 脚本核对 `CURRENT / CONFIRMED / PENDING / ATTEMPTS` 等状态，不只看发送进度。
5. 升级期间禁止运动，Flash 操作和复位不能与正常控制随意并行。

**项目关联**

10 月 6 日隔离测试固件由原 Bootloader 试运行，连续 5 秒检查 ADC、FOC 计算、编码器、UART 和硬关闭条件后正常确认。当天记录为 A confirmed、GEN=309；这是对应日期的测试状态，不是永远固定的槽位。见 [[20_真实网络Transfer与FOC并发_面试回答]]。

**追问：断电发生在元数据写到一半怎么办？**

启动时分别校验两副本，选择有效且代数合适的记录；写新副本时保留旧有效副本。具体掉电一致性见 Q048，仍需覆盖擦除、写入和提交各个断电点。

## Q054

**参考回答**

RPC 把远端能力表达为“调用服务中的方法，并得到对应结果”。`pw_rpc` 管理服务、方法、通道和调用编号；底层怎么送包由 transport 负责，Router 可以承担这部分转发。

```text
客户端调用 → pw_rpc 编码 → Router 送到目标节点
                                  ↓
客户端结果 ← Router 返回 ← 目标 pw_rpc 分派到服务方法
```

**Raw RPC 的含义**

Raw 表示业务 payload 由应用自行处理，不表示外层不用 protobuf。RPC packet 仍有协议规定的 channel、service、method、call_id 等字段；应用负载还要自己检查长度、范围和状态。

channel 是逻辑通信通道，不是物理 UART 编号。call_id 用来区分并发调用；设备重启、请求超时和晚到响应仍需要明确处理。

**项目关联**

我的 Router 已承载只读 Ping、状态和诊断类 RPC，真实 Transfer 服务也通过这层送包。实时 FOC ISR 不进入 RPC；协议、转发和 Transfer 在合适任务中处理，缓冲区和调用上下文各有限制。

早期 UART Raw Ping 使用小固定包和文本 HEX 承载；后来的 Router RPC 与 Transfer 是独立演进版本，不能把早期 96 字节包限制套到所有后续通道。详见 [[16_Router结合pw_rpc_白话实现与验证]]、[[20_真实网络Transfer与FOC并发_面试回答]]。

**追问：RPC 自动保证命令只执行一次吗？**

不保证。响应丢失时客户端可能重试；非幂等方法仍需命令身份、权限检查、去重和结果查询。只读接口通过不代表运动接口已经开放。

## Q055

**参考回答**

`pw_transfer` 在 `pw_rpc` 之上提供资源传输：用 session 和 offset 区分一次传输及每块位置，用窗口控制发送进度，通过重传和完成握手处理丢包与结束。它不是 CAN/UART 硬件驱动，也不只是把文件按固定长度切开。

**我的完整官方路径怎样用？**

1. MCU 注册只读资源 Handler，例如历史日志和编码器快照。
2. Handler 提供 Reader；历史日志冻结为一次传输的稳定快照，支持 Seek 回到需要重传的位置。
3. 官方 `TransferService` 和 `TransferThread` 处理协议状态、窗口、超时、重传和握手。
4. 客户端用官方 `Client.Read` 下载，完成后应用核对文件长度、格式及约定的整文件校验。
5. Router 只负责把完整 RPC packet 分片并转发，不为每个资源再写一套传输状态机。

**要分清三层**

| 层 | 解决的问题 | 我的项目例子 |
| --- | --- | --- |
| Transfer | 大资源的 offset、窗口、重传、完成 | 日志资源 3、编码器资源 4 |
| Router 分片 | 一个 RPC packet 超过单帧承载时怎样送达 | type 9 分片、整包重组与 CRC |
| 底层链路 | 字节或帧实际怎样走 | TCP、Wi-Fi、UART；CAN 有独立适配 |

**项目验收**

10 月 6 日实际走 PC → TCP → 鲁班猫 → Wi-Fi → ESP32 → UART → STM32，下载真实日志和 40 字节 `ENC1` 快照。CAN 历史导出也已接入官方引擎，但这次 Wi-Fi 多跳测试不是 CAN 实机导出的替代证据。见 [[12_CAN官方Transfer历史日志导出]]、[[20_真实网络Transfer与FOC并发_面试回答]]。

UART 固件升级保留原来的受限 Chunk 会话，并未因为加入官方只读下载就自动迁移。RAM 会话和快照也不支持宣称跨复位续传；网络固件写入没有开放。

**追问：Router 能转任意 Transfer，就代表任意文件都验收了吗？**

不代表。转发层不依赖具体资源，仍受包长、队列、权限、TTL 和重组容量约束。当前实机只验收资源 3/4；更大文件、任意资源和故障边界需单独测试。

## Q057

**参考回答**

日志不能为了“每条都打印”阻塞控制。常见设计是业务快速生成记录、放入有界队列，再由低优先级任务发送；队列满时按策略丢弃，并记录 drop 数量。

**我的日志记录怎样流转？**

```text
生成并封存共享记录
  ├→ 待发队列持有引用 → UART DMA 完成后释放
  ├→ history 持有引用 → 被覆盖/清空后释放
  └→ dump 或下载快照额外持有引用 → 用完后释放
最后一个引用释放 → 存储单元可以复用
```

共享引用减少重复 payload 缓存复制，但不能消除内存占用。慢消费者或同时持有多个快照会占住池，最终仍可能申请失败；引用计数更新和历史列表操作也有同步成本，不能称整个日志模块无锁。

**drop、history 和可靠记录有什么区别？**

drop 告诉我们有日志丢失，history 保存有限数量的近期记录，dump 导出一个稳定快照。history 不是无限队列，也不是持久化数据库；RAM 日志复位后会消失。重要工艺结果若要求可靠保存，需要独立的确认与持久化机制。

**项目关联**

日志高频路径避免长格式化和等待，发送任务与控制计算分离。实时 CAN 日志与官方 Transfer 历史下载可以并存：前者看最新事件，后者导出稳定记录，不把两者混成同一个协议。

**追问：为了不丢日志，把缓存不断加大可以吗？**

只能延缓溢出。长期输入速率高于输出速率，最终仍会满；应过滤、限速、摘要并暴露丢失计数，同时给关键事件单独保留预算。

## Q062

**参考回答**

AS5047P 的 SPI 响应有一帧流水线延迟：本次收到的值对应前一个命令。所以读取角度要先发读命令，再用后续帧取回结果，不能把第一帧直接当这次角度。

**驱动处理顺序**

1. 按 Mode 1、16 位帧和器件 CS 时序发送角度命令；项目使用 `FFFF` 后接 `C000`。
2. 对返回的 16 位响应检查偶校验，再判断 EF 错误标志。
3. 有错误时按事务规则读取/处理 ERRFL；错误帧不覆盖最后有效角度，也不刷新成功时间戳。
4. 正常结果取 14 位角度数据，保存样本序号、时间与质量状态，控制器检查年龄后再使用。

**为什么不能把芯片帧改成 CRC？**

校验格式由芯片硬件定义：bit 15 是 parity，bit 14 是 EF，bit 13:0 是数据。芯片没有在这个响应里发送 CRC，MCU 单方面改算法就没有可比对的 CRC 值，也不能向固定帧追加一段数据让芯片配合。

偶校验能检测奇数个位翻转，可能漏掉偶数个位翻转；CRC 的错误检测能力不同，不能说两者等价。

**项目关联**

SPI 驱动保留 parity/EF；编码器快照文件和 Router 整包另有软件 CRC32。这能检查 MCU 生成后的传输数据，却不能补救已经通过奇偶校验的 SPI 错值，也不证明磁铁状态或实际角度精度。DMA 驱动和实机边界见 [[17_SPI_DMA定时采样_白话实现与验证]]、[[18_SPI_DMA实机验收_20261006]]。

**追问：遇错继续用旧角度可以吗？**

可以保留 last-good 供诊断，但必须标记质量与年龄。控制器按过期规则处理，不能把旧值当新采样持续刷新时间。

## Q066

**参考回答**

ADC 应在电流信号相对稳定、且能代表所需相电流的时间窗口采样。PWM 开关瞬间有死区、驱动和放大器建立过程；离开关边沿太近，读到的可能是瞬态而不是可信电流。

**CH4 在这里做什么？**

TIM1 CH4 用作内部采样触发参考。软件根据三相比较值和电流检测拓扑，扣除死区、建立时间、触发延迟与采样孔径，再选可用的 CCR4；CH4 不是第四路电机相输出。

占空比变化后，采样窗口也会变化。因此 CCR1/2/3 与 CCR4 成组预装载，并交给自然更新事件生效，避免“新 PWM 配旧采样点”。仅关 CPU 中断不够，因为定时器硬件还在运行。

**双 ADC 配对为什么重要？**

FOC 使用的 U/V 电流必须来自同一批有效转换。不能 ADC1 已完成就直接拿 ADC2 的旧值；要检查配对完成状态，失败时按保护规则处理。

**项目验收边界**

已实现动态窗口规划、配对检查、耗时诊断和原始码统计，并完成隔离软件并发测试。逻辑分析仪可测数字 PWM/触发时序，不能直接证明模拟输入没有尖峰。95% 参考占空比能否可靠采样，仍取决于实际拓扑、恢复时间和模拟实测；参考占空比也不等于引脚扣除死区后的导通占比。见 [[19_FOC动态采样窗口_白话实现与验证]]。

**追问：怎么证明减少了一半中断？**

要在相同条件下对比改造前后的真实计数。共享 ADC IRQ 内调用两次 HAL 处理函数，不代表发生了两次硬件中断；原工程已经可能由 ADC1 单独通知。不能根据目标描述倒推一个没有测过的“40k → 20k”。

## Q068

**参考回答**

FOC 的核心是把三相电流换到跟随转子旋转的坐标系，分别调节 d 轴和 q 轴电流，再把电压指令转换为三相 PWM。这样能把磁场和转矩相关控制拆开，比直接给三相随意调占空比更容易闭环。

```text
相电流 → Clarke → α/β 电流 → Park（用电角）→ d/q 电流
                                                   ↓
PWM ← SVPWM ← 逆 Park ← 电压限幅 ← d/q PI
```

**关键原理**

Clarke 将三相量映射到静止 α/β 坐标，Park 再转换到旋转 d/q 坐标。电角由机械角、极对数、方向和零位偏置得到；角度、采样时刻或符号错了，坐标变换也会错。

PI 用目标与反馈的误差生成电压请求，再结合母线电压限幅并处理积分饱和。输出电压经逆变换与 SVPWM 生成三相比较值。具体归一化、符号和限幅必须和项目实现一致。

**项目关联**

10 月 6 日的隔离夹具实际运行原有 Clarke/Park、PI、限幅、逆 Park 和 SVPWM，并非只增加一个计数器。采样/计算平均约 20 kHz，但三相 PWM 输出关闭、计算出的占空比被丢弃，电机没有转动。

20 kHz 表示每秒约两万次计算，周期约 50 μs，不是两万转每秒，也不是网络下载频率。见 [[20_真实网络Transfer与FOC并发_面试回答]]。

**追问：`Iq` 就是真实扭矩吗？**

不是直接等号。在合适模型和标定下，q 轴电流与电磁转矩相关；真实拧紧扭矩还受电机常数、传动、摩擦和测量误差影响。没有独立扭矩参考和标定，不能把 `Iq` 曲线当高精度扭矩证明。

## Q108

**参考回答**

我会先画内存和所有权，不先说“用了原子操作”。新版 UART 生产者直接取得最终发送池，在里面生成数据；提交后由一个 TX 任务启动 DMA，完成才归还。无锁是固定池分配和 MPSC 发布核心，零拷贝是指定的发送与共享缓存路径，不是全系统标签。

**面试时可以画这两条线**

```text
UART 原生发送：Acquire → 原位生成 → Commit → DMA → Finish
日志共享：一次生成 → history/待发/dump 保存引用 → 各自用完释放
```

**把实现讲具体**

1. TX payload 池 8 KiB，32 个 256 字节单元，CAS 位图预留连续空间。
2. payload 写好再 release 发布；消费者 acquire 摘取，反转头插链表恢复本批发布顺序。
3. A 申请后被抢占，B 写完并提交，B 可以先发送，不按申请位置等 A。
4. Pigweed 封存共享记录，history 和待发队列持有引用，DMA 完成才释放发送引用。
5. 兼容 Write 接口仍复制任意调用者数据；RX 组行、Router 组包、Transfer 编码也不保证零复制。

**有哪些证据？**

主机测试覆盖地址一致、并发发布、慢生产者、旧租约、容量边界和 DMA 终止失败；早期每轮 60000 条消息、最终 10 轮共 600000 条是主机测试数量，不是实机帧数。115200 IAP 和实际回复已上板，2M 持续吞吐与完整故障压力仍缺实机证据。

**追问：这样保证每条消息完整了吗？**

队列设计保证的是受管理消息的所有权和发布规则；还要核对调用者没有越界写、DMA 没提前释放以及接收协议校验。成功 Commit 不等于线上的包已收到，DMA 完成也不等于业务已执行。
